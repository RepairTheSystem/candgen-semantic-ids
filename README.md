# Кандген для маркетплейса с повторами: семантические ID против dense и истории

Продолжение `repeat_switch/`: там одностадийная модель с переключателем «повтор / новое» на каталоге 1500 товаров.
Здесь — этап кандидатов на реальных данных (Instacart, ~25–50 тыс. товаров), где полный softmax по каталогу
и «всё в одной модели» уже не бесплатны.

## Зачем

Свежие работы по кандгену (обзор — в переписке, ссылки ниже):

- генеративный ретривал по **семантическим ID** (TIGER → OneRec, PinRec, Sona) заменяет ANN-индекс генерацией
  токенов товара; Sona (Yandex Music, 2026) одной моделью заменила каскад из 15+ кандгенов;
- «How Well Does Generative Recommendation Generalize?» (2026): SID-модели сильнее там, где нужно **обобщение**,
  item-ID модели — где нужно **запоминание**, и адаптивное смешивание на запрос улучшает обе.
  В маркетплейсе повтор — это запоминание, новое — обобщение: это наш переключатель, перенесённый на кандген;
- гибриды SID + dense (LIGER, COBRA) лечат слабость SID на редких / новых товарах.

**Гипотезы**

- **H1.** SID-ретривал лучше dense на новых товарах и особенно на хвосте; на повторах лучше история / ID-модели.
- **H2.** Переключатель между источниками на запрос (сколько из K слотов отдать истории) лучше фиксированной квоты.

## Источники кандидатов

| источник | что делает |
|----------|------------|
| `pop` | популярность в train |
| `hist` | товары истории пользователя, Σ 0.9^(заказов назад) — только повторы |
| `hist+pop` | `hist`, остаток — популярное (классический бейзлайн next-basket) |
| `dense` | SASRec-энкодер + dense-ретривал, sampled softmax (2048 равномерных негативов на батч), точный MIPS |
| `dense-exp` | `dense` без товаров истории — источник «нового» |
| `sid-text` | генеративный ретривал: SID из текста товара (TF-IDF «название \| ряд \| отдел» → SVD → residual k-means), декодер + constrained beam search |
| `sid-cf` | то же, SID из эмбеддингов обученной dense-модели (коллаборативные SID) |
| `sid-*-exp` | SID без товаров истории |
| `hybrid-*` | SID-кандидаты (beam 2K) → доранжирование dense-скором (LIGER-подобно) |
| `union[src, fixed / switch / oracle / hist-first]` | K слотов: q из `hist` + (K − q) из источника нового. `fixed` — q подобран на val; `switch` — q = α·K·p̂, p̂ — регрессор доли повторов в следующей корзине (признаки истории, обучен на последнем train-заказе), α на val; `oracle` — истинная доля; `hist-first` — вся история, потом новое |

Энкодер у dense и SID одинаковый (трансформер над последними 100 товарами истории + паузы между заказами
+ время с последнего заказа до запроса). Вход SID-энкодера — сумма эмбеддингов SID-токенов товара.

## Протокол и метрики

- Instacart без календарных дат: время = сумма `days_since_prior_order` (обрезано на 30 дней).
- **test-цель — последний заказ пользователя, val — предпоследний**; модель учится на заказах до val,
  на тесте история включает val-заказ (стандарт next-basket на Instacart: глобального времени нет).
- Обучающие запросы: последние `--per-user` заказов train каждого пользователя, цель — вся следующая корзина.
- Ранняя остановка по val Recall@50.
- **Recall@K** по пользователям и микро-Recall отдельно по **повторам**, **новому** и **новому из хвоста**
  (не входит в топ-20% товаров по частоте), `coverage@100`, латентность одного запроса (batch=1) до top-K.
- Урок из `repeat_switch`: источники «нового» исключают **всю** историю пользователя, а не окно.

## Результаты v1 (Kaggle GPU, 1 сид)

28 667 пользователей, 24 149 товаров, средняя тестовая корзина 10.4 товара, **61% товаров корзины — повторы**,
медиана различных товаров в истории — 47. Сырые файлы — `results/kaggle_v1/`.

**Источники, Recall@K (тест)**

| источник | R@10 | R@50 | R@100 | R@200 | explore@100 | explore-tail@100 | coverage@100 |
|---|---|---|---|---|---|---|---|
| hist+pop | **0.352** | **0.585** | **0.644** | **0.685** | 0.096 | 0 | — |
| dense | 0.159 | 0.315 | 0.404 | 0.502 | 0.171 | 0.0147 | 0.79 |
| sid-text | 0.143 | 0.285 | 0.366 | 0.455 | 0.175 | 0.0030 | 0.31 |
| sid-cf | 0.138 | 0.280 | 0.363 | 0.457 | 0.179 | 0.0022 | 0.29 |
| hybrid-text | 0.152 | 0.308 | 0.396 | 0.489 | 0.189 | 0.0053 | 0.32 |
| pop (explore-часть) | | | | | 0.151 | 0 | 0.004 |

Источники «нового» (`-exp`, explore-Recall): dense 0.042 / 0.127 / 0.189 / 0.275 при K = 10 / 50 / 100 / 200;
sid-cf 0.046 / 0.133 / 0.197 / 0.279; на хвосте dense 0.017 против 0.003 у SID при K=100.

**Выводы**

1. **История — главный источник.** `hist+pop` при K=10 даёт в 2.2 раза больше dense; dense догоняет только к K≈200,
   и то не догоняет (0.50 против 0.685). Это известный результат для next-basket
   ([Li et al., A Next Basket Recommendation Reality Check](https://arxiv.org/abs/2109.04584)):
   повторы дают основную часть качества, «новое» угадывается плохо. Обученные источники нового лишь
   на ~25% лучше популярного (explore@100: 0.19 против 0.15).
2. **H1 — отвергнута в части хвоста.** На «новом» в целом SID чуть лучше dense, стабильно при всех K
   (sid-cf-exp +0.004…+0.008, без бутстрепа). Но на хвосте SID в **5–7 раз хуже**, coverage 0.29–0.32 против 0.76:
   beam search по префиксам тянет к популярным кластерам. Гибрид (кандидаты SID → dense-скор) поднимает общий Recall SID
   (0.366 → 0.396), но всё равно ниже dense, потому что ограничен тем, что нашёл beam, и хвост почти не лечит.
   Плюс SID — в 6 раз меньше параметров (285 тыс. против 1.66 млн, нет таблицы эмбеддингов товаров).
3. **H2 — в таком виде проверять нечего.** Подобранная на val квота q = K (вся история, потом новое) почти везде;
   переключатель с α = 2…5 вырождается в то же самое; Recall совпадает до 4-го знака. Слот истории в разы
   «дороже» слота нового, а истории (медиана 47 товаров) хватает, чтобы занять почти все K ≤ 50.
   Корреляция p̂ с долей повторов 0.53 — предсказывать её можно, только на кандгене это не нужно.
4. **Ошибка в постановке:** `oracle` (q = K · истинная доля повторов) — **не верхняя граница**, он хуже `fixed`
   (0.315 против 0.352 при K=10). Делить слоты пропорционально доле повторов неоптимально: решает
   вероятность попадания на слот, а не доля. Честная верхняя граница — q, лучший для каждого пользователя по его цели.
5. **Латентность (GPU, batch=1):** hist+pop 0.6 мс, dense 2.4 мс, SID beam 200 — 10.2 мс (×4.3), гибрид — 12.9 мс.
   На 24 тыс. товаров точный MIPS почти бесплатен. Цена beam от размера каталога почти не зависит,
   поэтому на 10⁸ товаров (где dense нужен ANN-индекс) соотношение будет другим — здесь это не измерено.
6. **Недообучение:** dense и оба SID упёрлись в `--max-epochs 30` (лучшие эпохи 30 / 27 / 29), val Recall dense ещё
   растёт. Разрыв dense–SID может измениться; CF-SID построены из недообученных эмбеддингов.
   Text-SID: только 8 537 уникальных кодов на 24 тыс. товаров (78% товаров в коллизиях, до 160 в группе) — текст
   «название | ряд | отдел» слишком однороден, и последний токен фактически становится ID товара.

**Что сделать в v2:** max-epochs 80; верхняя граница по пользователю вместо `oracle`; парный бутстреп
SID-exp против dense-exp; разбивка по длине истории (короткая история — единственное место, где
переключатель может что-то дать); text-SID без ряда/отдела или с балансированным k-means, чтобы уменьшить коллизии.

## Ограничения (заранее)

- ~25–50 тыс. товаров — не индустриальный масштаб; разницу методов видно, абсолютную латентность — нет.
- SID из TF-IDF названий проще, чем из LLM-эмбеддингов (в окружении без интернета так надёжнее);
  `--sid-sources text+cf` — комбинированный вариант.
- Декодер обусловлен только состоянием пользователя (без cross-attention на всю историю, как в TIGER) — дешевле,
  но слабее; dense и SID делят одинаковый энкодер, так что сравнение честное.
- Один сид по умолчанию.
